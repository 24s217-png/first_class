# Burger King UI Coding Guide

## 1. 프로젝트 기본 원칙

- 기존 프로젝트의 HTML 구조와 CSS 작성 방식을 우선한다.
- 이미 작성된 코드를 확인한 뒤 필요한 부분만 수정한다.
- 새로운 화면을 만들 때도 기존 로그인 화면의 구조와 스타일을 최대한 재사용한다.
- 복잡한 라이브러리보다 현재 수업에서 배운 HTML/CSS/JavaScript를 우선한다.

## 2. 현재 프로젝트 구조

```text
first_class
├── bk
│   ├── login.html
│   └── img
├── css
│   └── default.css
└── font
    └── ...
```

## 3. 기준 화면

기준 파일: `bk/login.html`

기존 로그인 화면의 구조를 새로운 버거킹 회원 관련 화면 제작의 기준으로 사용한다.

주요 구조:
- `#wrap`
- `header`
- `main`
- `form`
- `fieldset`
- `.input_box`
- `.login_option`
- `.login_link`
- `.sns_login`

## 4. HTML 작성 원칙

- 콘텐츠의 의미에 맞는 시맨틱 태그를 사용한다.
- 화면 모양만 보고 무조건 `div`로 작성하지 않는다.
- 페이지의 주요 제목은 `h1`, 주요 영역은 `h2` 등으로 계층을 구분한다.
- 입력 요소에는 필요한 경우 `label`과 `id`를 연결한다.
- `button`은 역할에 맞게 `type`을 지정한다.
- 이미지나 아이콘을 사용할 때 대체 텍스트 또는 스크린리더용 텍스트를 고려한다.

## 5. div 사용

div는 의미가 없는 레이아웃용 그룹에 사용한다.

예:
```html
<div class="input_box">
    ...
</div>
```

단, 의미가 있는 영역이라면 `header`, `nav`, `main`, `section`, `article`, `footer` 등의 시맨틱 태그를 먼저 검토한다.

## 6. 기존 스타일에서 유지할 것

- 버거킹 기존 컬러 변수
- 기존 폰트
- `#wrap`의 기본 레이아웃
- `main`의 기본 여백
- `input`의 기본 크기와 모서리
- 버튼의 기본 스타일
- 기존 이미지 경로 방식
- 기존 `default.css` 활용 방식

## 7. 브랜드별 변경

버거킹 화면을 새로 만들 때는 다음 요소를 화면 목적에 맞게 변경한다.
- 제목
- 안내 문구
- 입력 항목
- 버튼 문구
- 오류/도움말 문구
- 화면에 필요한 아이콘
- 화면별 간격

기존 로그인 화면의 스타일을 유지하면서 콘텐츠와 필요한 구조만 변경한다.

## 8. CSS 변수

기존 `login.html`의 변수를 우선 활용한다.

```css
:root {
  --font: "Sandoll GothicNeoRound", sans-serif;
  --font-Pre: "Pretendard Variable", sans-serif;
  --font-BKR: "BKR", sans-serif;
  --primary: #512314;
  --disabledBg: #DDCDBE;
  --focus: #D62302;
  --baseBorder: #D9CFC6;
  --baseBg: #FFFCF9;
  --button: #E9DDCD;
  --errorColor: #C54734;
  --placeholder: #EBE6E2;
  --text: #766053;
  --bg: #f4ebdc;
}
```

새로운 색상을 무작정 추가하기보다 기존 변수를 먼저 확인한다.

## 9. 이미지와 폰트 경로

`bk` 폴더 안의 HTML에서 이미지 경로는 기존 방식에 맞춘다.

예:
```html
<img src="img/파일명.svg" alt="설명">
```

CSS에서도:
```css
background-image: url(img/파일명.svg);
```

상위 폴더의 폰트와 공통 CSS는 기존 경로 방식을 유지한다.

## 10. 접근성

- `input`에는 사용자가 무엇을 입력해야 하는지 알 수 있도록 `label` 또는 적절한 안내를 제공한다.
- 아이콘만 있는 버튼에는 스크린리더가 읽을 수 있는 텍스트를 제공한다.
- 장식용 이미지는 `alt=""`를 사용하는 방법도 검토한다.
- 키보드로 사용할 수 있는 버튼과 입력 요소의 상태를 고려한다.

## 11. 폼 요소

로그인/회원 관련 화면은 `form`을 중심으로 구성한다.

예:
```html
<form action="" method="post">
    <fieldset>
        <legend class="sr-only">로그인</legend>
        ...
    </fieldset>
</form>
```

입력 요소의 `id`와 `label`의 `for`가 연결되는지 확인한다.

## 12. 기존 코드 수정 원칙

전체 코드를 새로 작성하기 전에 다음을 확인한다.

1. 현재 코드에서 어떤 부분이 문제인지 찾는다.
2. 문제가 HTML인지 CSS인지 확인한다.
3. 파일 경로와 이미지 파일이 실제로 존재하는지 확인한다.
4. 기존 코드로 해결할 수 있는지 먼저 생각한다.
5. 필요한 부분만 수정한다.

## 13. 코드 작성 시 주의할 점

현재 프로젝트에서 발견된 대표적인 실수:
- 같은 CSS 선언을 중복 작성하지 않는다.
- `padding: 0 -20px`처럼 잘못된 값을 사용하지 않는다.
- 서로 다른 `input`을 띄어쓰기만으로 연결하는 잘못된 CSS 선택자를 사용하지 않는다.
- CSS 선언을 작성할 때 세미콜론과 속성 구문을 정확하게 작성한다.
- `label`의 `for`와 `input`의 `id`가 실제로 연결되는지 확인한다.
- `button`의 용도에 따라 `type`을 지정한다.

## 14. 화면 제작 순서

1. Figma 화면에서 콘텐츠를 확인한다.
2. 화면의 의미와 사용자 행동을 파악한다.
3. 기존 `login.html`에서 재사용할 구조를 찾는다.
4. HTML 구조를 먼저 작성한다.
5. 기존 CSS 변수와 레이아웃을 활용한다.
6. 필요한 부분만 CSS를 추가한다.
7. 이미지와 폰트 경로를 확인한다.
8. 브라우저에서 실제 화면을 확인한다.
9. 모바일 크기에서도 확인한다.
10. 기존 코드와 비교하여 불필요한 코드가 없는지 확인한다.

## 15. AI에게 코드를 요청할 때

- 기존 코드를 먼저 분석한다.
- 기존 구조를 유지한다.
- 필요한 부분만 수정한다.
- 새로운 라이브러리를 임의로 추가하지 않는다.
- 코드만 주지 말고 중요한 변경 이유를 설명한다.
- 문제가 있는 경우 완성 코드보다 먼저 원인을 설명한다.
- 파일 경로와 연결 상태를 확인한다.

## 16. 최종 점검

### HTML
- 시맨틱 구조가 적절한가?
- 제목 계층이 자연스러운가?
- form과 input 구조가 적절한가?
- label과 input이 연결되어 있는가?
- button type이 적절한가?

### CSS
- 기존 변수를 재사용했는가?
- 중복 코드가 없는가?
- 잘못된 선택자가 없는가?
- 이미지 경로가 맞는가?
- 모바일 화면에서 깨지지 않는가?

### 접근성
- 아이콘 버튼을 스크린리더가 이해할 수 있는가?
- 입력 항목을 이해할 수 있는가?
- 키보드 사용이 가능한가?

### 프로젝트 일관성
- 기존 Burger King `login.html`의 스타일과 코드 방식에서 지나치게 벗어나지 않았는가?
- 기존 파일 구조와 경로를 유지했는가?
